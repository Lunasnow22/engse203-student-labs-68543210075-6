## 1. ภาพรวม (Data Model Overview)

ระบบ Campus Service Request มีการออกแบบโครงสร้างฐานข้อมูลเชิงสัมพันธ์ (Relational Database) โดยแบ่งออกเป็น 2 ตารางหลักที่มีความสัมพันธ์กันแบบ **One-to-Many (1:N)**:

```text
┌───────────────────────┐             ┌──────────────────────────────────┐
│         users         │ 1         N │             requests             │
├───────────────────────┤             ├──────────────────────────────────┤
│ id (PK, INTEGER)      │────────────<│ id (PK, TEXT)                    │
│ name (TEXT)           │             │ requester_id (FK -> users.id)    │
│ department (TEXT)     │             │ request_type (TEXT)              │
│ email (TEXT, UNIQUE)  │             │ location (TEXT)                  │
└───────────────────────┘             │ details (TEXT)                   │
                                      │ priority (TEXT)                  │
                                      │ status (TEXT)                    │
                                      │ created_at (TEXT)                │
                                      └──────────────────────────────────┘
```

- **ความสัมพันธ์:** ผู้ใช้ 1 คน (`users`) สามารถสร้างคำร้อง (`requests`) ได้หลายรายการ แต่ละคำร้องจะถูกสร้างโดยผู้ใช้เพียงคนเดียวเท่านั้น ผ่านคอลัมน์ `requester_id` ซึ่งเป็น Foreign Key

## 2. ทำไมต้องแยกเป็น 2 ตาราง (Separation of Concerns & Normalization)

ในสัปดาห์ก่อนหน้า (Week 06–07) ข้อมูลถูกเก็บเป็น JSON ก้อนเดียว โดยเก็บข้อมูลผู้แจ้ง (`requesterName`) ฝังซ้ำๆ ในทุกรายการคำร้อง ซึ่งก่อให้เกิดปัญหาสำคัญดังนี้:

1. **ปัญหาความซ้ำซ้อนของข้อมูล (Data Redundancy):** หากผู้ใช้คนเดิมสร้าง 20 คำร้อง ข้อมูลชื่อและแผนกของผู้ใช้คนนั้นจะถูกบันทึกซ้ำกันถึง 20 ครั้ง ทำให้เปลืองพื้นที่จัดเก็บ
2. **ปัญหาความไม่สอดคล้องของข้อมูลเมื่อแก้ไข (Update Anomaly):** ถ้าสมชายเปลี่ยนชื่อหรือย้ายแผนก ในระบบเดิมเราต้องตามไปแก้คำร้องทุกใบของสมชาย หากหลุดไปแม้แต่ใบเดียว จะทำให้ข้อมูลขัดแย้งกันทันที แต่เมื่อแยกตาราง `users` ออกมา เราสามารถ**แก้ไขที่ตาราง `users` เพียงที่เดียว ข้อมูลคำร้องทั้งหมดจะถูกต้องตรงกันทั้งระบบทันที**
3. **ปัญหาการลบข้อมูล (Deletion Anomaly):** หากผู้ใช้ลบคำร้องทั้งหมดทิ้ง ในระบบเดิมข้อมูลของผู้ใช้คนนั้นจะสูญหายไปด้วย แต่เมื่อแยกตาราง แม้จะไม่มีคำร้องเหลืออยู่ ข้อมูลบัญชีผู้ใช้ก็ยังคงอยู่ในระบบอย่างสมบูรณ์

## 3. รายละเอียดตารางและ Constraints

### ตาราง `users`
| คอลัมน์ | ชนิดข้อมูล | Constraints | เหตุผลในการเลือก |
|---|---|---|---|
| `id` | `INTEGER` | `PRIMARY KEY AUTOINCREMENT` | ให้ฐานข้อมูลสร้างรหัสผู้ใช้เป็นตัวเลขอัตโนมัติและไม่ซ้ำกัน |
| `name` | `TEXT` | `NOT NULL` | ชื่อผู้ใช้เป็นข้อมูลจำเป็น ห้ามเป็นค่าว่าง |
| `department` | `TEXT` | `NOT NULL` | แผนก/สาขาวิชา จำเป็นสำหรับการติดต่อประสานงาน |
| `email` | `TEXT` | `NOT NULL UNIQUE` | อีเมลต้องห้ามว่างและห้ามซ้ำกัน เพื่อใช้เป็นข้อมูลระบุตัวตน |

### ตาราง `requests`
| คอลัมน์ | ชนิดข้อมูล | Constraints | เหตุผลในการเลือก |
|---|---|---|---|
| `id` | `TEXT` | `PRIMARY KEY` | รองรับรหัสคำร้องตามรูปแบบธุรกิจ เช่น `REQ-001` |
| `requester_id` | `INTEGER` | `NOT NULL, REFERENCES users(id)` | เชื่อมโยงกับผู้ใช้ ห้ามเป็นค่าว่าง และป้องกันการสร้างคำร้องโดยไม่มีผู้ใช้จริง |
| `request_type` | `TEXT` | `NOT NULL, CHECK (request_type IN (...))` | จำกัดเฉพาะ 4 ประเภทคำร้องที่ระบบรองรับ |
| `location` | `TEXT` | `NOT NULL` | สถานที่เกิดเหตุ ห้ามเป็นค่าว่าง |
| `details` | `TEXT` | `NOT NULL` | รายละเอียดคำร้อง ห้ามเป็นค่าว่าง |
| `priority` | `TEXT` | `NOT NULL DEFAULT 'normal', CHECK (...)` | จำกัดเฉพาะ `normal` หรือ `urgent` กำหนดค่าเริ่มต้นเป็น normal |
| `status` | `TEXT` | `NOT NULL DEFAULT 'pending', CHECK (...)` | จำกัดสถานะเป็น `pending`, `in-progress`, `completed` |
| `created_at` | `TEXT` | `NOT NULL DEFAULT (datetime('now','localtime'))` | บันทึกวันเวลาที่สร้างคำร้องอัตโนมัติ |

## 4. เหตุผลของการเลือกชนิดข้อมูลและ Constraints

1. **ทำไม `users.id` กับ `requests.id` ใช้ชนิดต่างกัน:**
   - `users.id` ใช้ `INTEGER PRIMARY KEY AUTOINCREMENT` เพื่อประสิทธิภาพการสร้างรหัสภายในระบบที่เร็วและนับลำดับได้ง่าย
   - `requests.id` ใช้ `TEXT PRIMARY KEY` เพื่อให้รหัสคำร้องมีความหมายสำหรับมนุษย์ (Human-readable ID) เช่น `REQ-001` ซึ่งตรงกับ Contract เดิมของระบบ
2. **ทำไมต้องมี CHECK constraint ทั้งที่ API ตรวจข้อมูลแล้ว:**
   - เป็นการป้องกันแบบ **Defense-in-Depth (หลายชั้น)** เพราะข้อมูลอาจถูกเพิ่มผ่านช่องทางอื่นได้ เช่น การยิงคำสั่ง SQL โดยตรง, Batch Job, หรือเกิด Bug ในฝั่ง API การมี Constraint ที่ระดับฐานข้อมูลจะรับประกันได้ 100% ว่าจะไม่มีข้อมูลผิดพลาดหลุดเข้าไปในระบบ

## 5. ตัวอย่างการใช้ JOIN ดึงข้อมูล

คำสั่ง SQL ในการดึงคำร้องพร้อมชื่อและแผนกของผู้แจ้ง:

```sql
SELECT 
  r.id,
  r.request_type,
  r.location,
  r.status,
  u.name AS requester_name,
  u.department
FROM requests r
JOIN users u ON r.requester_id = u.id
ORDER BY r.created_at DESC;
```

**ผลลัพธ์ที่ได้:**
| id | request_type | location | status | requester_name | department |
|---|---|---|---|---|---|
| REQ-001 | แจ้งซ่อม | ห้องปฏิบัติการ 301 | pending | สมชาย ใจดี | วิศวกรรมซอฟต์แวร์ |
| REQ-002 | บริการบัญชีผู้ใช้ | อาคารวิศวกรรม | in-progress | สุภาวดี รักเรียน | วิศวกรรมซอฟต์แวร์ |
| REQ-003 | ขอใช้อุปกรณ์ | ห้องประชุม 2 | completed | ธนกฤต ตั้งใจ | วิศวกรรมไฟฟ้า |

## 6. ข้อสังเกตสำหรับการนำไปใช้ในสัปดาห์ที่ 10 (Backend Integration)

ผลลัพธ์จากการทำ `JOIN` จะให้ข้อมูลในรูปแบบ Flat Table ที่มีฟิลด์ `requester_name` ออกมาเหมือนกับ Response JSON ที่ React เคยได้รับใน Week 07 ทุกประการ ทำให้ใน Week 10 เมื่อเราเปลี่ยนจากการอ่าน JSON มาใช้ `db.prepare(...).all()` ฝั่ง Frontend React จะสามารถนำข้อมูลไปแสดงผลต่อได้ทันทีโดยไม่ต้องแก้โค้ดฝั่งหน้าบ้านเลย
